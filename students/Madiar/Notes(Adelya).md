# Этап 2. Primary Key и Foreign Key

## 3. Что такое Primary Key?

`Primary Key` — первичный ключ, который уникально идентифицирует запись.

Например:

```
Composer
----------------
id | name
1  | Бетховен
2  | Шопен
```

У двух строк не может быть одинакового `id`, если это первичный ключ.

## 4. Что такое Foreign Key?

`Foreign Key` — внешний ключ, который связывает одну таблицу с другой.

Например:

```
Composer
----------------
id | name
1  | Бетховен
2  | Шопен

Work
---------------------------------
id | title          | composer_id
1  | Лунная соната  | 1
2  | Ноктюрн        | 2
3  | Симфония № 5   | 1
```

Здесь `composer_id = 1` означает, что произведение связано с Бетховеном.

Один композитор может иметь много произведений.

Это отношение называется **One-to-Many (один ко многим)**.

\<text>Схема связи:\</text>

```
Composer (1)
    |
    | написал
    |
    v
Work (много)
```

# Этап 3. Изучаем Django ORM

## 5. Что такое ORM?

ORM расшифровывается как Object-Relational Mapping.

Это технология, позволяющая работать с реляционной базой данных через Python-объекты.

Без ORM можно написать SQL:

```
SELECT * FROM composer;
```

С Django ORM:

```
Composer.objects.all()
```

Обе операции могут использоваться для получения записей композиторов.

Django ORM самостоятельно формирует необходимые SQL-запросы.

Однако ORM не заменяет знание SQL.

Ты должен понимать, какие действия выполняются в базе.

## 6. Создаём первую модель

```
from django.db import models


class Composer(models.Model):
```

### Разбор по строкам

`class Composer` — создаём класс модели.

`models.Model` — указываем Django, что класс представляет модель данных.

`CharField` — текстовое поле с ограничением длины.

`max_length=150` — максимальная длина строки.

`__str__()` — определяет текстовое представление объекта.

Django обычно автоматически создаёт поле первичного ключа `id`, если ты не указал его самостоятельно.

# Этап 4. Связи в Django

## 7. ForeignKey

Пример модели произведения:

```
class Work(models.Model):
    title = models.CharField(max_length=200)

    composer = models.ForeignKey(
        Composer,
        on_delete=models.PROTECT,
        related_name="works"
    )

    difficulty = models.PositiveSmallIntegerField()

    def __str__(self):
        return self.title
```

Здесь:

`title` — название произведения.

`composer` — ссылка на композитора.

`on_delete=models.PROTECT` — запрещает удалять композитора, если на него ссылаются произведения.

`related_name="works"` — позволяет получить произведения композитора через `composer.works.all()`.

`difficulty` — число сложности. В этом учебном примере допустимые значения пока дополнительно не ограничены.

## 8. Что означает on_delete?

Изучи четыре варианта:

| Вариант    | Поведение                                        |
| ---------- | ------------------------------------------------ |
| `CASCADE`  | Удаляет связанные записи вместе с объектом       |
| `PROTECT`  | Запрещает удаление при наличии связанных записей |
| `SET_NULL` | Устанавливает NULL, если поле допускает NULL     |
| `RESTRICT` | Ограничивает удаление с учётом защищённых связей |

# Этап 5. Many-to-Many

## 9. Что делать, если у произведения несколько композиторов?

Рассмотрим другую модель.

В ней произведение может быть связано с несколькими композиторами.

И один композитор может иметь несколько произведений.

Это **Many-to-Many (многие ко многим)**.

Пример:

```
class Composer(models.Model):
    name = models.CharField(max_length=150)


class Work(models.Model):
    title = models.CharField(max_length=200)

    composers = models.ManyToManyField(
        Composer,
        related_name="works"
    )
```

Django автоматически создаст промежуточную таблицу для связи.

Схематично:

```
Composer
---------
id
name
   |
   |
   v
WorkComposer
-------------
composer_id
work_id
   ^
   |
   |
Work
---------
id
title
```

## 10. Как работает промежуточная таблица?

Например:

**Composer**

| id | name     |
| -- | -------- |
| 1  | Бетховен |
| 2  | Моцарт   |

**Work**

| id | title                |
| -- | -------------------- |
| 1  | Учебное произведение |

**WorkComposer**

| work_id | composer_id |
| ------- | ----------- |
| 1       | 1           |
| 1       | 2           |

Это означает, что одно произведение связано сразу с двумя композиторами.

## 11. Явная промежуточная модель

Когда нужно хранить дополнительные данные о связи, можно создать отдельную модель.

Например:

```
class Composer(models.Model):
    name = models.CharField(max_length=150)


class Work(models.Model):
    title = models.CharField(max_length=200)

    composers = models.ManyToManyField(
        Composer,
        through="WorkComposer",
        related_name="works"
    )


class WorkComposer(models.Model):
    work = models.ForeignKey(
        Work,
        on_delete=models.CASCADE
    )

    composer = models.ForeignKey(
        Composer,
        on_delete=models.CASCADE
    )

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["work", "composer"],
                name="unique_work_composer"
            )
        ]
```

Обрати внимание на `through="WorkComposer"`.

Это означает, что Django будет использовать нашу явную промежуточную модель.

`UniqueConstraint` запрещает повторять одну и ту же пару произведение–композитор.

Создай:

- 4 произведения;
- 6 связей.

Проверь, что повторяющаяся пара нарушает уникальность.

# Этап 6. Миграции Django

## 12. Что такое миграции?

Представь, что ты написал новую модель.

Просто написать Python-класс недостаточно.

Нужно изменить структуру базы данных.

Для этого Django использует миграции.

### Команда 1

```
python manage.py makemigrations
```

Django анализирует изменения моделей и создаёт файлы миграций.

### Команда 2

```
python manage.py migrate
```

Django применяет миграции к базе данных.

Команды нужно выполнять из каталога, где расположен `manage.py`, с правильно настроенным Django-окружением.

Если проект запускается через Docker, сначала спроси Кирилла или преподавателя, как правильно выполнить эти команды в контейнере.

# Этап 9. Производительность ORM

## 24. Что такое проблема N+1?

Представь, что в базе 100 произведений.

Ты сначала получаешь список произведений, а затем для каждого отдельно загружаешь композитора.

В результате приложение может выполнить много SQL-запросов.

Это называют проблемой N+1.

## 25. select_related()

Для ForeignKey:

```
works = Work.objects.select_related("composer")
```

Django может получить произведения и связанных композиторов с помощью SQL JOIN.

## 26. prefetch_related()

Для ManyToMany:

```
works = Work.objects.prefetch_related("composers")
```

Django отдельно загружает связанные записи и сопоставляет их в Python.

# Этап 10. Ограничения базы данных

## 27. Зачем нужны ограничения?

Представь, что сложность произведения задаётся числом от 1 до 5.

Но кто-то записал:

```
difficulty = 999
```

Такие данные некорректны по нашему учебному правилу.

Можно использовать ограничение:

```
class Work(models.Model):
    title = models.CharField(max_length=200)
    difficulty = models.PositiveSmallIntegerField()

    class Meta:
        constraints = [
            models.CheckConstraint(
                condition=(
                    models.Q(difficulty__gte=1)
                    & models.Q(difficulty__lte=5)
                ),
                name="work_difficulty_1_to_5"
            )
        ]
```

Этот пример рассчитан на актуальный синтаксис Django с аргументом `condition`.

### Изучи ограничения

- `unique=True`
- `UniqueConstraint`
- `CheckConstraint`
- `null=False`
- `ForeignKey`

# Этап 11. Тестирование моделей

## 28. Зачем нужны тесты?

Тесты проверяют, действительно ли код ведёт себя так, как мы ожидаем.

Например, можно проверить, что композитор сохраняется в базе.

```
from django.test import TestCase


class ComposerModelTest(TestCase):

    def test_create_composer(self):
        composer = Composer.objects.create(
            name="Бетховен"
        )

        self.assertEqual(
            composer.name,
            "Бетховен"
        )
```

Класс `TestCase` использует тестовую базу данных и изолирует изменения между тестами.

Тебе нужно использовать корректный импорт `Composer` из своего учебного Django-приложения.

## 29. Что необходимо протестировать?

Создай тесты, которые проверяют:

1. Создание композитора.
2. Создание произведения.
3. Связь произведения с композитором.
4. Запрет недопустимого значения сложности.
5. Уникальность связей WorkComposer.
6. Получение всех произведений композитора.
7. Поиск по названию.
8. Корректность выбранного `on_delete`.

Пример проверки количества:

```
def test_composer_count(self):
    Composer.objects.create(name="Бетховен")
    Composer.objects.create(name="Шопен")

    self.assertEqual(
        Composer.objects.count(),
        2
    )
```

## 30. Как запустить тесты?

В Django:

```
python manage.py test
```

Команду запускать только в правильно настроенном окружении проекта. Убедись, что конфигурация тестовой базы безопасна и не указывает на рабочую базу данных.

# Этап 12. PostgreSQL и Docker

## 31. Что такое PostgreSQL?

PostgreSQL — реляционная система управления базами данных.

Она хранит таблицы, проверяет ограничения, выполняет SQL-запросы и поддерживает транзакции.

Django ORM работает поверх PostgreSQL и других поддерживаемых баз данных.

## 32. Что такое Docker?

Docker помогает запускать приложение и его зависимости в изолированных контейнерах.

В нашем проекте предусмотрен `docker-compose.yml`.

Обычно через Docker Compose можно организовать работу:

- Django.
- PostgreSQL.
- Frontend.

Однако в Music Sheet Library полноценный запуск контейнеров пока не был подтверждён: раньше доступ к Docker Engine завершился ошибкой.
