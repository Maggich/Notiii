Он отправляет HTTP-запрос:


Django получает запрос, выполняет необходимую логику и отправляет ответ:

```json
[
  {
    "id": 1,
    "title": "Лунная соната",
    "difficulty": 3
  },
  {
    "id": 2,
    "title": "Ноктюрн",
    "difficulty": 2
  }

```

Это учебный пример. Реальный API-контракт пока не утверждён.

## 3. HTTP-методы

| Метод | Назначение |
|---|---|
| GET | Получение данных |
| POST | Создание данных |
| PUT | Полная замена ресурса |
| PATCH | Частичное обновление |
| DELETE | Удаление |

В публичном каталоге на первом этапе в основном потребуются GET-запросы.

POST, PUT, PATCH и DELETE изучаются на учебном API. Не нужно открывать публичное изменение произведений без отдельного решения преподавателя.

### Задание 1.2

Изучи HTTP-статусы:

- `200 OK` — успешный запрос.
- `201 Created` — ресурс создан.
- `204 No Content` — успешный ответ без тела.
- `400 Bad Request` — ошибка запроса.
- `401 Unauthorized` — требуется действительная аутентификация.
- `403 Forbidden` — доступ запрещён.
- `404 Not Found` — ресурс не найден.
- `405 Method Not Allowed` — метод не разрешён.
- `500 Internal Server Error` — внутренняя ошибка сервера.

**Приёмка:** преподаватель называет ситуацию, а ты объясняешь, какой статус должен вернуть API и почему.

# Этап 4. Query Parameters

## 7. Что такое параметры запроса?

Например:

```http
GET /api/works/?search=соната
```

Всё после `?` — параметры запроса.

В Django их можно получить так:

```python
search = request.GET.get("search", "")
```

Теперь можно использовать введённый текст для поиска.

Пример:

```python
def works_list(request):
    search = request.GET.get("search", "")

    results = [
        work
        for work in WORKS
        if search.lower() in work["title"].lower()
    ]

    return JsonResponse({"results": results})
```


Ожидается корректный список совпадений или пустой список.

```python
def parse_positive_int(value, default):
    if value is None:
        return default

    try:
        number = int(value)
    except (TypeError, ValueError):
        raise ValueError("Ожидается целое число")

    if number < 1:

    return number
```

# Этап 7. Django REST Framework и Serializer

## 10. Что такое Serializer?

Когда Django получает модель из базы, она представлена Python-объектом.

Чтобы отправить данные на frontend, необходимо преобразовать их в подходящий формат ответа.

В Django REST Framework для этого используются сериализаторы.

**Django REST Framework пока не утверждён как зависимость проекта.** Следующий пример — учебный. Устанавливать библиотеку в основной проект можно после согласования.

Пример:

```python
from rest_framework import serializers


class WorkSerializer(serializers.Serializer):
    id = serializers.IntegerField()
    title = serializers.CharField()
    difficulty = serializers.IntegerField()
```

Использование:

```python
serializer = WorkSerializer(work)

print(serializer.data)
```

# Этап 8. Pagination — постраничная загрузка

## 11. Зачем нужна пагинация?

Представь, что в музыкальном каталоге 50 000 произведений.

Если сервер вернёт все произведения сразу, ответ может быть слишком большим.

Поэтому данные разбивают на страницы.

Например:

```http
GET /api/works/?page=1&limit=10
```

Это первая страница из десяти произведений.

### Задание 8.1

Сделай учебную пагинацию.

Формат ответа для упражнения:

```json
{
  "page": 1,
  "limit": 10,
  "count": 25,
  "results": []
}
```

Поля означают:

- `page` — номер страницы.
- `limit` — количество элементов на странице.
- `count` — общее количество подходящих записей.
- `results` — произведения текущей страницы.

# Этап 9. Обработка ошибок

## 12. API должен возвращать понятные ошибки

Плохой вариант — сервер падает и пользователь видит технический traceback.

Вместо этого API должен выдавать контролируемый ответ.

Например:

```json
{
  "error": {
    "code": "INVALID_PAGE",
    "message": "Номер страницы должен быть положительным"
  }
}
```

Это предлагаемый учебный формат ошибок.

- Отсутствующие данные.
- Ошибка обращения к базе данных.

# Этап 12. Автоматические тесты API

## 15. Почему тесты обязательны?

API может работать правильно в одном случае и ломаться в другом.

Поэтому для каждого endpoint нужны тесты.

В обычном Django можно использовать:

```python
from django.test import TestCase, Client


class WorkApiTests(TestCase):
    def setUp(self):
        self.client = Client()

    def test_health(self):
        response = self.client.get("/api/v1/health/")

        self.assertEqual(response.status_code, 200)
```

Этот тест проверяет HTTP-статус существующего health endpoint.

Мадиар отвечает за схему данных, а frontend-команда — за отображение.

Твоя работа считается готовой только тогда, когда:

- API соответствует утверждённому контракту;
- запросы возвращают корректные данные;
- некорректные запросы обрабатываются предсказуемо;
- тесты проходят;
- frontend-команда может использовать API;
- преподаватель проверил результат;
- ты можешь объяснить свой код без подсказок.
